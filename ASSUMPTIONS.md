# Assumptions & Deviations

Honest, consolidated record of every deviation from spec, every assumption made, and every deferred/stubbed piece of work across all build phases. This is not marketing copy — if something is incomplete or approximated, it says so here.

## Dependency & tooling choices

- **`@supabase/supabase-js` pinned to `2.45.4` and `@supabase/ssr` to `0.5.1`** (exact versions, not caret ranges) in `package.json`. Newer `@supabase/supabase-js` (2.116+) ships a stricter PostgREST query-parser that broke this project's hand-written `types/database.ts` typing for some nested-embed queries. Pinning was the pragmatic fix; revisiting the hand-written types to work with the newer parser is future work, not done here.
- **Font**: the system font stack (see `app/globals.css`), not `next/font`'s Google Fonts loader or the spec's suggested "GI Sans" / "Anek" — those aren't publicly distributable web fonts, and depending on `fonts.google.com` at build time breaks on networks/CI that block it. `app/layout.tsx` documents this choice inline.
- **No Storybook / component-catalog tool** was set up — out of scope given the spec's own file-structure list didn't call for one.

## Architecture decisions inherent to Next.js App Router

- **Route groups don't add URL segments.** `(admin)`, `(mentor)`, `(participant)` are organizational only — `app/(admin)/ideas/page.tsx` and a hypothetical `app/(mentor)/ideas/page.tsx` would collide on the exact same `/ideas` URL. This is why `/overview` is a single shared `app/overview/page.tsx` that branches on the viewer's active role in code (see its own doc comment) rather than three separate per-role files, and why every route name across roles had to be planned as one flat namespace up front.
- **Middleware route-prefix lists must be kept in sync by hand.** `middleware.ts` maintains `PARTICIPANT_PREFIXES` / `MENTOR_PREFIXES` / `ADMIN_PREFIXES` / `SHARED_PROTECTED_PREFIXES` as plain arrays checked against the request path — there is no single source of truth deriving this from the nav config or the route groups themselves. `/voting-management` and `/showcase-content` were initially missing from `ADMIN_PREFIXES` (caught and fixed in this phase) purely because they were added to the app after the array was first written; the per-route-group `layout.tsx` guard is the actual enforcement backstop for exactly this reason, so this was a defense-in-depth gap, not an access-control hole.

## Postgres function / RLS design choices

- **`fn_vote_tallies` admin bypass** (`0010_fn_vote_tallies_admin_bypass.sql`): the original function refused to return tallies for anyone until `results_published`. The spec requires admins to see live turnout before publication (the one role allowed to), so the function was extended with an `is_admin(auth.uid())` bypass rather than adding a second function, to keep one call site.
- **Voting's publish step is application code, not `fn_publish_batch`.** `fn_publish_batch` is keyed on "one row per idea, per program" (screening/qualifier/mentor/final/showcase all fit that shape); a voting period is one row per program, not per idea, so `publishVotingResults` (`lib/services/voting-management.ts`) implements the same publish→publications-row→audit-log→notify pattern directly in application code instead of forcing it through `fn_publish_batch`'s idea-keyed shape.
- **The participant-safe column exposure for screening/qualifier/final-presentation results is row-level, not column-level** — see `SECURITY.md`'s "Known limitations" section for the full explanation. This is an accepted tradeoff of the security-barrier-view design, not something fixed in this phase, because Postgres/Supabase's shared-role model can't express column-level RLS that varies by caller.
- **`idea_status` enum only has `draft`/`submitted`** — there's no explicit `screened`/`qualified`/`showcased` status on the `ideas` table itself. Idea Management's "stage" filter (`lib/ideas/stage.ts`) is therefore *derived* at query time from the presence/publication of `screening_decisions`/`qualifier_assessments`/`showcase_projects` rows, computed in JS after one fetch, rather than a single indexed SQL column. Fine at the idea volumes this program operates at (hundreds, not millions); would need to become a real column + index at a much larger scale.

## Deferred / stubbed work (explicitly, not silently)

- **Cron is documented, not wired.** `app/api/cron/voting-notifications/route.ts` exists, is `CRON_SECRET`-protected, and does the right thing when invoked, but nothing in this repo schedules it — that's a deployment-time step (Vercel Cron / a company cron daemon) documented in `VERCEL_DEPLOYMENT.md` and `COMPANY_SERVER_DEPLOYMENT.md`.
- **Email is queued, not sent.** `lib/email/adapter.ts`'s only implementation (`DevOutboxEmailAdapter`) inserts into `email_outbox` and `console.log`s. A real SMTP/Microsoft Graph adapter implementing the same `EmailAdapter` interface is a documented TODO, not built — there was no real mail server available to integrate against in any phase of this build.
- **E2E tests are written, not executed.** Every file under `tests/e2e/` (beyond the original `sign-in.spec.ts` smoke test) was authored against this app's actual component structure and documented with exactly what live Supabase/seed-data state each scenario requires, but this sandbox cannot download Playwright's browser binaries — `npx playwright install chromium` fails with `403 request blocked: no rule or allowlist entry allows host "cdn.playwright.dev"`. These need to be run for real, in an environment with that network access, before being trusted in CI. See the phase report for the exact error.
- **Integration tests use a hand-rolled fake Supabase client, not a real Postgres.** `tests/integration/helpers/fake-supabase.ts` and the reviewer-routing / publish-batch mirror tests exercise real service-layer app code (auth gating, Zod parsing, request shaping) plus a JS port of the documented contract of `fn_route_reviewer`/`fn_publish_batch`/`fn_submit_vote` — they do not verify the SQL migrations themselves. That needs a real Supabase/Postgres test project; every integration test file's header comment says so explicitly.
- **CI pipeline is not included.** No `.github/workflows/*.yml` (or equivalent) was requested or added — `npm run typecheck && npm run lint && npm run build && npm run test` is documented as the verification sequence but isn't wired into an actual CI runner in this repo.

## Notification/audit gaps found and fixed during this build (not spec deviations, but worth naming since they weren't there originally)

- `fn_route_reviewer` never notified the mentor it successfully assigned a review to — only the routing-required admin-escalation path notified anyone. Fixed in `0015_voting_lifecycle_and_reviewer_notify.sql`.
- `fn_publish_batch` originally notified every idea owner in the whole program on every publish call, not just the ones actually in that batch. Fixed in `0012_fn_publish_batch_notify_fix.sql`.
- The Project Showcase page's embedded idea/team-leader/team-member fields, and `ideas_participant_view`'s published screening/qualifier/final-presentation fields, were both silently nulled out by missing RLS SELECT policies (there was no participant-facing read policy on those tables at all). Fixed in `0013_showcase_visibility_rls.sql` and `0014_participant_safe_view_rls_fix.sql` respectively.

## Anything else assumed outright

- **"Submission open/close" and "showcase open" toggles** (Program Configuration spec wording) are implemented as timestamp fields (`submission_open_at`, etc.) with a "set to now" quick action, not as separate boolean flag columns — there's no `is_submission_open` column in the schema, and the existing date-based design (used everywhere else in the app to gate stage visibility) already expresses "open" as "now is after open_at and before close_at". Adding parallel boolean flags would have meant two sources of truth for the same thing.
- **Program Configuration's FAQ entries** are stored as `program_content` rows keyed `faq_<timestamp>`, reusing that table rather than adding a new one — `program_content` already exists precisely for admin-editable program text (`key`/`title`/`body`), and the spec didn't call for a dedicated FAQ table.
- **Demo/seed credentials** (`README.md`'s table) are fake, local-development-only values (`AideaDemo!2026`) fixed in `scripts/seed.ts` — never meant to represent real production credentials, and called out as fake in every place they're printed.

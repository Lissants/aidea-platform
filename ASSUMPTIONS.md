# Assumptions & Deviations

Honest, consolidated record of every deviation from spec, every assumption made, and every deferred/stubbed piece of work across all build phases. This is not marketing copy — if something is incomplete or approximated, it says so here.

## Dependency & tooling choices

- **Supabase client libraries were removed** with the move to SQL Server (see "SQL Server migration" below), and with them the earlier exact-version pin of `@supabase/supabase-js` / `@supabase/ssr` that worked around the newer PostgREST query-parser. Database access is now `mssql`, with the `msnodesqlv8` driver (Windows auth, local default, an optional dependency) or `tedious` (TCP + SQL login, Docker/Linux).
- **Font**: the system font stack (see `app/globals.css`), not `next/font`'s Google Fonts loader or the spec's suggested "GI Sans" / "Anek" — those aren't publicly distributable web fonts, and depending on `fonts.google.com` at build time breaks on networks/CI that block it. `app/layout.tsx` documents this choice inline.
- **No Storybook / component-catalog tool** was set up — out of scope given the spec's own file-structure list didn't call for one.

## Architecture decisions inherent to Next.js App Router

- **Route groups don't add URL segments.** `(admin)`, `(mentor)`, `(participant)` are organizational only — `app/(admin)/ideas/page.tsx` and a hypothetical `app/(mentor)/ideas/page.tsx` would collide on the exact same `/ideas` URL. This is why `/overview` is a single shared `app/overview/page.tsx` that branches on the viewer's active role in code (see its own doc comment) rather than three separate per-role files, and why every route name across roles had to be planned as one flat namespace up front.
- **Proxy route-prefix lists must be kept in sync by hand.** `proxy.ts` maintains `PARTICIPANT_PREFIXES` / `MENTOR_PREFIXES` / `ADMIN_PREFIXES` / `SHARED_PROTECTED_PREFIXES` as plain arrays checked against the request path — there is no single source of truth deriving this from the nav config or the route groups themselves. `/voting-management` was initially missing from `ADMIN_PREFIXES` (caught and fixed in this phase) purely because it was added to the app after the array was first written; the per-route-group `layout.tsx` guard is the actual enforcement backstop for exactly this reason, so this was a defense-in-depth gap, not an access-control hole.

## Stored procedure / authorization design choices

- **`usp_vote_tallies` admin bypass** (originally `fn_vote_tallies`, `supabase/migrations/0010_fn_vote_tallies_admin_bypass.sql`): the original function refused to return tallies for anyone until `results_published`. The spec requires admins to see live turnout before publication (the one role allowed to), so the procedure lets admins through (`dbo.fn_has_role(@actor_id, 'admin')`) rather than adding a second procedure, to keep one call site.
- **Voting's publish step is application code, not `usp_publish_batch`.** `usp_publish_batch` is keyed on "one row per idea, per program" (screening/qualifier/mentor/final all fit that shape); a voting period is one row per program, not per idea, so `publishVotingResults` (`lib/services/voting-management.ts`) implements the same publish→publications-row→audit-log→notify pattern directly in application code instead of forcing it through `usp_publish_batch`'s idea-keyed shape.
- **Participant-safe result columns — limitation no longer applies.** Under Supabase, participants read screening/qualifier/final-presentation results through `ideas_participant_view`, whose protection was row-level only (see `SECURITY.md`'s "Known limitations"). That view was dropped in the SQL Server migration: participant-facing queries now select only published rows and only the safe columns they need (never `internal_reason`, scores or admin comments), so the column-exposure gap is closed.
- **`ideas.status` only allows `draft`/`submitted`** — there's no explicit `screened`/`qualified` status on the `ideas` table itself. Idea Management's "stage" filter (`lib/ideas/stage.ts`) is therefore *derived* at query time from the presence/publication of `screening_decisions`/`qualifier_assessments` rows, computed in JS after one fetch, rather than a single indexed SQL column. Fine at the idea volumes this program operates at (hundreds, not millions); would need to become a real column + index at a much larger scale.

## SQL Server migration

The platform moved from Supabase (Postgres + Auth + Storage) to a local Microsoft SQL Server 2019 database. Decisions made along the way:

- **Schema translation.** Postgres enums became `NVARCHAR` + `CHECK` constraints, `uuid` → `UNIQUEIDENTIFIER`, `timestamptz` → `DATETIMEOFFSET(3)`, `jsonb` → `NVARCHAR(MAX)` + `ISJSON`. Migrations are T-SQL files in `db/migrations/` applied by `npm run db:migrate` and tracked in `dbo.schema_migrations`. `supabase/` is kept only as historical reference; its RLS policies and `supabase/RLS_TEST_MATRIX.md` remain the authorization spec.
- **`NO ACTION` foreign keys.** SQL Server rejects multiple cascade paths into one table, so `reviews.idea_id` and `final_presentation_assessments.program_id` are `NO ACTION`. Their rows are still deleted through the other cascade path (via `review_assignments` or `ideas`).
- **Functions became stored procedures.** The plpgsql `fn_*` functions are now `usp_*` procedures (`usp_submit_idea`, `usp_route_reviewer`, `usp_submit_review`, `usp_reopen_review`, `usp_publish_batch`, `usp_submit_vote`, `usp_vote_tallies`) plus `dbo.fn_has_role` / `dbo.fn_is_idea_team_member`. `auth.uid()` became an explicit `@actor_id` parameter, and each procedure checks the actor again.
- **Authentication was replaced.** Supabase Auth → `dbo.users` (email, bcrypt `password_hash`, `entra_oid`) plus an app-signed HS256 JWT cookie `aidea_session` (`SESSION_SECRET`, 8-hour lifetime, sliding refresh in `proxy.ts`). Sign-in is email + password, or optional Microsoft Entra ID SSO (authorization code + PKCE). SSO checks the tenant and `ALLOWED_EMAIL_DOMAIN`, and links to an existing account by Entra object id first, then by email.
- **Magic-link sign-in was removed.** It depended on Supabase Auth's email delivery, and there is no working mail sender (see "Email is queued, not sent" below).
- **SSO default roles.** A first-time SSO user gets `SSO_DEFAULT_ROLES` (default `participant,employee_voter`). Mentor and admin roles are still granted by an admin.
- **Authorization moved into the app.** There is no RLS: the app connects with one SQL login. Rules are enforced in service-layer SQL through `lib/permissions/scopes.ts` (row filters that mirror the old RLS policies), admin checks, and the actor checks inside the procedures.
- **Profile search** (`/api/profiles/search`, used to add team members) is available to every signed-in user and returns only id, name and email, top 10 matches.
- **Wider profile visibility.** Mentor names are visible to every signed-in user (mentor preference picker), and mentors can see the names of the team on any submitted idea. The Supabase-era policies hid these, so the picker showed "Mentor" and the review page showed "Unknown".
- **`audit_logs` is now actually written.** Under Supabase, application-side audit writes were silently blocked because RLS had no insert policy on `audit_logs`. They now succeed (`lib/audit/log.ts`, admin sessions only), alongside the rows written inside the procedures.
- **Files are stored on local disk.** Supabase Storage → files under `UPLOAD_DIR`, served by `/api/files/[bucket]/[...key]`. Program resources need a session, and uploads are admin-only. The upload directory must be backed up together with the database, and it rules out Vercel (see `VERCEL_DEPLOYMENT.md`).
- **CSV export timestamps** are now written as ISO-8601 UTC strings ending in `Z` (e.g. `2026-03-01T09:30:00.000Z`), where Postgres previously produced its own `+00:00` text format.

## Deferred / stubbed work (explicitly, not silently)

- **Cron is documented, not wired.** `app/api/cron/voting-notifications/route.ts` exists, is `CRON_SECRET`-protected, and does the right thing when invoked, but nothing in this repo schedules it — that's a deployment-time step (a company cron job or Windows scheduled task calling the route with `Authorization: Bearer <CRON_SECRET>`).
- **Email is queued, not sent.** `lib/email/adapter.ts`'s only implementation (`DevOutboxEmailAdapter`) inserts into `email_outbox` and `console.log`s. A real SMTP/Microsoft Graph adapter implementing the same `EmailAdapter` interface is a documented TODO, not built — there was no real mail server available to integrate against in any phase of this build.
- **E2E tests are written, not executed.** Every file under `tests/e2e/` (beyond the original `sign-in.spec.ts` smoke test) was authored against this app's actual component structure and documented with exactly what seeded database state each scenario requires, but this sandbox cannot download Playwright's browser binaries — `npx playwright install chromium` fails with `403 request blocked: no rule or allowlist entry allows host "cdn.playwright.dev"`. These need to be run for real, in an environment with that network access, before being trusted in CI. See the phase report for the exact error.
- **Integration tests now run against real SQL Server.** The earlier hand-rolled fake Supabase client is gone: `tests/integration/` creates a throwaway `aidea_test` database, applies the real migrations and seed, and runs the service code and stored procedures against it (see `LOCAL_SETUP.md`). They need a reachable SQL Server instance to run.
- **CI pipeline is not included.** No `.github/workflows/*.yml` (or equivalent) was requested or added — `npm run typecheck && npm run lint && npm run build && npm run test` is documented as the verification sequence but isn't wired into an actual CI runner in this repo.

## Notification/audit gaps found and fixed during this build (not spec deviations, but worth naming since they weren't there originally)

These were fixed in the Supabase migrations named below. The fixed behaviour carries over to the SQL Server procedures.

- `fn_route_reviewer` never notified the mentor it successfully assigned a review to — only the routing-required admin-escalation path notified anyone. Fixed in `0015_voting_lifecycle_and_reviewer_notify.sql`; `usp_route_reviewer` notifies the mentor.
- `fn_publish_batch` originally notified every idea owner in the whole program on every publish call, not just the ones actually in that batch. Fixed in `0012_fn_publish_batch_notify_fix.sql`; `usp_publish_batch` notifies only the owners in the batch.
- `ideas_participant_view`'s published screening/qualifier/final-presentation fields were silently nulled out by a missing RLS SELECT policy (there was no participant-facing read policy on those tables at all). Fixed in `0014_participant_safe_view_rls_fix.sql`. With RLS gone, the same visibility rules now live in `lib/permissions/scopes.ts` and the participant queries.

## Anything else assumed outright

- **"Submission open/close" toggles** (Program Configuration spec wording) are implemented as timestamp fields (`submission_open_at`, etc.) with a "set to now" quick action, not as separate boolean flag columns — there's no `is_submission_open` column in the schema, and the existing date-based design (used everywhere else in the app to gate stage visibility) already expresses "open" as "now is after open_at and before close_at". Adding parallel boolean flags would have meant two sources of truth for the same thing.
- **Program Configuration's FAQ entries** are stored as `program_content` rows keyed `faq_<timestamp>`, reusing that table rather than adding a new one — `program_content` already exists precisely for admin-editable program text (`key`/`title`/`body`), and the spec didn't call for a dedicated FAQ table.
- **Demo/seed credentials** (`README.md`'s table) are fake, local-development-only values (`AideaDemo!2026`, overridable with `DEMO_PASSWORD`) set in `scripts/seed.ts` — never meant to represent real production credentials, and called out as fake in every place they're printed.
- **Voting candidates are every finalized Build idea.** The Project Showcase was removed (`db/migrations/0004_remove_showcase.sql`). The Voting page lists every idea in the program whose qualifier assessment is finalized with `build_decision = 'build'`, whether or not that result has been published yet, and `usp_submit_vote` rejects votes for any other idea. The same rule makes those ideas' titles and team members readable to any signed-in user (`lib/permissions/scopes.ts`).
